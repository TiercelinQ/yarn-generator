# /yarn-run-tests - Executable verification

## Role
QA engineer - prove the project is clean, buildable, and runnable with real commands.

## Goal
Run the verification ladder, surface any failure with its output, and confirm a clean state or hand off failures to `/yarn-fix-issue`.

## Deliverable
A short report in the user's language stating what passed, with command output as proof; or a list of failures.

---

> If the project root has not been provided in this flow, first ask: `Project root? (folder path)`.

## Steps

1. **Apply `@rules/verification.md §A`** in order (the use case is read from `docs/specs/04-architect.md`; `yarn install`, `yarn run <script>` and `yarn <script>` are verified in `yarn-berry-cli-reference/yarn-install.md` and `yarn-run.md`):
   ```
   yarn install                 # dependencies resolve
   yarn typecheck               # tsc --noEmit - expect clean
   yarn lint                    # eslint (flat config) - expect clean
   yarn build                   # tsup (Node targets) or Vite (UI) - produces the entry bundle
   yarn test                    # vitest run - only if tests were enabled (Phase 1); else skip
   ```
   Then the **smoke of the use case** (exact commands in `@rules/verification.md`):
   ```
   node dist/cli.js --help      # CLI tool - prints usage, exit 0
   node dist/cli.js --version   # CLI tool - prints the version, exit 0
   ```
   For the other use cases, run the smoke that `@rules/verification.md` defines (library: the built entry imports without error · service: the server starts and answers a health or smoke request, then stops · extension: the bundle builds, host loading is out of automatic scope · application: the Vite build completes and the output is served or previewed).
   - **Smoke scope**: for a CLI, `--help` / `--version` exercise the CLI wiring (commander parse, composition root, exit-0 path) **without an org**. When Salesforce coupling is confirmed, the **full** smoke of real `sf` operations (a live `sf data query`, a `sf project deploy`) needs an **authenticated org** reachable through `sf` - that is **out of automatic scope**. State it; never fake it. The same holds for anything needing an external system (a host application for an extension, a deployed environment for a service).
   - The static read-through (`@rules/verification.md §B`) confirms: layering respected, no secret logged, CLI: stdout carries data only and exit codes map at the boundary (`error` → 1 / `warning` → 0 / `ValidationError` → 2; an empty dataset is a success, exit 0); with Salesforce: every `sf` call goes through `src/sf/runner.ts` via `cross-spawn` (args array, no spawn from a `services`/adapter module). Tests never spawn the real `sf` - the runner is mocked (`@rules/tests.md`).

2. **Capture output**. A non-zero exit or any reported error is a failure - quote the relevant lines as proof.

3. **Report** (in the user's language, per `@rules/verification.md §C`):
   - All clean → **one short confirmation line** (no full checklist recap), with the proof commands.
   - Any discrepancy → name the command / failing check + the `file:line`, and hand off to `/yarn-fix-issue` for the root cause (do not patch here unless the user asks).
   - The org-dependent or external-system smoke that could not run → state it plainly and list the exact commands the user must run themselves (with Salesforce: against an authenticated org).

4. If the **Node/Yarn environment is not available**: say so plainly, do the static read-through (`@rules/verification.md §B`), and list the exact commands the user must run themselves. **Never claim a clean typecheck / build you could not execute.**

## Test creation policy

- Tests are opt-in at Phase 1. If enabled, the suite (`vitest`) was delivered in its dedicated batch - run it (`yarn test`, exit 0).
- **Do not create a test suite if the project has none.** The default verification is typecheck + lint + build + smoke.
- If the user **explicitly asks** to add tests later: follow `@rules/tests.md` (`vitest`; `node` environment for a CLI, library or service; `jsdom` + `@testing-library/react` for a project with UI; mock `cross-spawn` and the fs read when Salesforce is confirmed; layer coverage; French test names). Confirm scope, then add `vitest` as a dev dependency with `yarn add --dev vitest` (verified in `yarn-add.md`) + the `"test": "vitest run"` script (+ an optional `vitest.config.ts`). For a UI project, pin the current minor of `jsdom` and `@testing-library/react` at that time, confirmed with `yarn npm info <package>` (`yarn-npm-info.md`).

## Anti-patterns - what NOT to do
- **Do not** report "all green" without having actually run the commands (or without flagging that the env was unavailable).
- **Do not** fix code silently inside this skill - verification reports; fixing is `/yarn-fix-issue` (root cause) or `/yarn-add-feature`.
- **Do not** scaffold tests or add a test runner the user did not ask for.
- **Do not** lower a check (skip typecheck, disable a lint rule, drop the smoke) to make the report pass.
- **Do not** claim the org-dependent `sf` smoke (Salesforce) or any external-system smoke passed - it is out of automatic scope; list it for the user.
- **Do not** run `npm`, `npx` or `pnpm`, or a `yarn` command/flag not verified in `yarn-berry-cli-reference/`.
- **Do not** rewrite the README - this skill is read-only; at most flag it stale for a write skill (`@rules/readme.md`).

## When the user asks something adjacent
- **"Make the build pass"** → if it fails, the root cause is in code/config; classify with `/yarn-fix-issue`. Do not disable checks to force green.
- **"Add coverage"** → that is explicit test creation; confirm scope + runner, then write tests per `@rules/tests.md`.
