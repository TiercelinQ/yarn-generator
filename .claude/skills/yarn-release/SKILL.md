# /yarn-release - Cut a SemVer release

## Role
Release manager - turn the accumulated changes into a clean, versioned, GitHub-ready release.

## Goal
Stamp the pending `[Unreleased]` changelog entries into a dated SemVer version block, bump the version at its single source, keep every version location consistent, and (only on explicit confirmation) run the publication step of the release channel.

## Deliverable
Updated `docs/release/CHANGELOG.md` (a new released block + reset `[Unreleased]`), the bumped version source, a copy-pasteable release note, and (if confirmed) the published artifact.

---

## Prerequisite

The project must be loaded (`/yarn-load-project`, OR `docs/specs/04-architect.md` / README present). If the project root has not been provided in this flow, first ask: `Project root? (folder path)`.

Load context: `@rules/versioning.md` (+ `@rules/verification.md` + `@rules/distribution.md`). Read the use case from `docs/specs/04-architect.md`: it selects the release channel in `@rules/distribution.md`.

For any `yarn` command in Steps 4 and 6, read `yarn-berry-cli-reference/yarn-index.md`, then only the needed file (`yarn-version.md`, `yarn-pack.md`, `yarn-npm-publish.md`) **before** running it. Never `npm`, `npx` or `pnpm`.

## Step 1 - Read the current state

1. Read `docs/release/CHANGELOG.md`.
   - **Absent** → the project predates the changelog system. Stop and route to `/yarn-load-project` (it proposes the retroactive initialization). Do not create it here.
   - Present → read the `## [Unreleased]` section and the current top released version.
2. Read the canonical version: `package.json` `"version"`.

## Step 2 - Nothing to release?

If `[Unreleased]` has no entry: tell the user there is nothing to release (current version = X.Y.Z) and stop. Do not create an empty version block.

## Step 3 - Infer and propose the increment

Apply the inference of `@rules/versioning.md`:
1. Any `**BREAKING:**` marker or a `Removed` entry → **MAJOR**.
2. Else any `Added` entry → **MINOR**.
3. Else (only `Fixed` / internal `Changed`) → **PATCH**.

Compute the three candidate versions from the current one. Ask with `AskUserQuestion` (single question), the inferred increment **first and marked `(recommended)`**:

- `MAJOR → <x+1>.0.0` - [what counts as breaking for the use case, per `@rules/versioning.md`: a renamed/removed command, flag, endpoint or public export, a changed exit-code semantics or `stdout` data shape (CLI), a changed response shape or status code (service), a changed default behavior, a removed config key]
- `MINOR → <x>.<y+1>.0` - new backward-compatible feature(s)/capability
- `PATCH → <x>.<y>.<z+1>` - fixes / internal changes only

Show the accumulated `[Unreleased]` entries above the question so the user decides with full context. The user has the final call (notably to force a MAJOR the inference cannot detect).

## Step 4 - Apply the release

On confirmation, using the chosen version `NEW` and the session date `<YYYY-MM-DD>`:

1. In `docs/release/CHANGELOG.md`: rename `## [Unreleased]` content into a new block `## [NEW] - <YYYY-MM-DD>` (keep the category order Added/Changed/Fixed/Removed/Security), and insert a fresh empty `## [Unreleased]` above it.
2. Bump the **canonical** version with Yarn: `yarn version NEW --immediate` (an explicit semver is a valid strategy, `--immediate` applies the change right away even if `preferDeferredVersions` is set; verified in `yarn-version.md`). Preview with `yarn version NEW --dry-run` if the user wants to see the result first. It updates `package.json` `"version"`. **That is the only version to write** - `src/config.ts` `APP_VERSION` is read from `package.json` (`import pkg from "../package.json" with { type: "json" }`, then `pkg.version`), so it follows automatically; there is nothing else to sync (`@rules/config.md`, `@rules/versioning.md`).
3. Update the README **title line** to the new version: `# [PROJECT_NAME] - v[NEW]` - a **targeted edit** of that single line, never a full README regeneration (`@rules/readme.md §When to refresh`).
4. Do **not** touch `docs/specs/`, the rest of the README (only the title line above moves), or the project `CLAUDE.md` origin (that records the framework version, not the project version).

## Step 5 - Verify + hand off

1. Apply `@rules/verification.md` version consistency: the top released version == `package.json` `"version"` (== the derived `APP_VERSION`, no separate mirror to edit); the README title line shows `v[NEW]`; `[Unreleased]` reset empty. Run `yarn typecheck`, `yarn lint` and `yarn build` so the release artifact is built from the bumped version.
2. Output the cut version block verbatim in a fenced markdown snippet - ready to paste into a GitHub release.
3. Remind the user that committing and tagging are theirs to do (this skill never commits): e.g. `git commit -am "release: vNEW"` then `git tag vNEW`.

## Step 6 - Publication (release channel of the use case)

Read the release channel of the use case in `@rules/distribution.md`. **Publishing is outward-facing and hard to reverse**: this skill never runs a publication command on its own. Show the exact command(s) first, then ask for confirmation with `AskUserQuestion` (options: `Publish now (recommended)` · `Dry run only` · `Skip, I publish myself`). Run it only on an explicit yes. Never publish a version whose Step 4-5 are not complete.

By use case:

- **CLI tool, npm registry** and **library, npm registry**:
  1. Inspect the content of the package without producing it: `yarn pack --dry-run` (lists the files of the archive, verified in `yarn-pack.md`). Check the `files` / `bin` / `exports` entries and that `dist/` is built.
  2. Check the registry login: `yarn npm whoami` (verified in `yarn-index.md`). If not logged in, tell the user to run `yarn npm login` themselves (credentials are never typed or logged by this skill).
  3. After confirmation: `yarn npm publish` (verified in `yarn-npm-publish.md`). Add `--access public` for a public scoped package, `--tag <tag>` for a non-`latest` dist-tag (prerelease), `--otp <code>` only if the user supplies it. `yarn npm publish --dry-run` shows what would be published without publishing; `--staged` puts the package on hold for approval (`yarn npm stage approve`, `yarn-npm-stage.md`) instead of publishing immediately.
- **CLI tool, personal** (no registry): nothing to publish. The tool runs locally with `yarn dev` or `node dist/cli.js` (after `yarn build`). `yarn link` installs no global command: it is run from **another (consumer) project** (`yarn link <path-to-this-project>`, verified in `yarn-link.md`) and adds a `resolutions` entry there; mention it only if the user wants to consume this CLI from such a project. Skip the confirmation.
- **Service, personal only** (default, nothing recorded in Phase 1): there is nothing to publish. Tag only after the bump (surface the `git tag` command), no publication command, no confirmation needed.
- **Service, external** (only if Phase 1 recorded a target and artifact format in `docs/specs/01-scoping.md`): follow `@rules/distribution.md` and use the target the user recorded. Run only a command the user gave or that is verified; if none is recorded, stop at the version bump and hand the release note over.
- **Extension, personal** (default): when host = VS Code, build the `.vsix` with `vsce` and install it by hand (`@rules/distribution.md`); for another host, package and install per the contract the user stated in Phase 1. Nothing to publish, no confirmation needed.
- **Extension, host store** (only if Phase 1 recorded it): when host = VS Code, the exact publish command is defined by the `vscode` framework, not by this skill; for another host, use only the publish command the user stated in Phase 1. Do not write one from memory; if none is given, stop at the version bump and hand the release note over.
- **Application, personal only** (default): there is nothing to publish. Tag only after the bump, `yarn build` then `yarn preview` or the built `dist/` for personal use, no publication command, no confirmation needed.
- **Application, external** (only if Phase 1 recorded a target and artifact format): `yarn build` produces the artifact; hand it to the target the user recorded. No publication command is run by this skill unless the user gave it and confirmed it.

The external channel of a service, extension or application runs only if Phase 1 recorded it. Read it from `docs/specs/01-scoping.md`; absent means personal only.

After a publication, report the command run and its outcome. A failed publication is reported as is; never retry with different flags or another package manager without the user.

## Anti-patterns - what NOT to do
- **Do not** create the changelog here if it is absent - route to `/yarn-load-project`.
- **Do not** cut a release with an empty `[Unreleased]`.
- **Do not** apply a MAJOR without explicit user confirmation.
- **Do not** hand-edit `src/config.ts` `APP_VERSION` - it is derived from `package.json`; bump `package.json` `"version"` only, via `yarn version`.
- **Do not** rewrite or reword past released blocks - only `[Unreleased]` moves.
- **Do not** commit or tag - surface the commands, let the user run them.
- **Do not** run `yarn npm publish` (or any publication command) without an explicit confirmation of this very publication, in this session.
- **Do not** type, store or log registry credentials or an OTP the user did not supply; `yarn npm login` is the user's action.
- **Do not** invent a `yarn` command or flag - verify against `yarn-berry-cli-reference/`; never use `npm`, `npx` or `pnpm`.

## When the user asks something adjacent
- **"Just bump to X.Y.Z"** → honor an explicit version, but still move `[Unreleased]` into the dated block.
- **"Release and push to GitHub"** → do the changelog + version bump; the actual commit/tag/push stays the user's action (surface the commands).
- **"Publish it"** → run Step 6 for the use case, with the confirmation gate; the publication is never implied by the version bump.
