# /yarn-trace-feature - Analyze a generated yarn project

## Role
Analyst - trace and explain how a feature works across the layers, without changing it.

## Goal
Give the user an accurate, layered understanding of a feature or behavior, with exact code references - including, where applicable, where the `sf` call happens (Salesforce only) and where a `Result` maps to the boundary outcome (CLI: exit code; service: status code).

## Deliverable
A structured report (in the user's language) with `file:line` references. Optionally `docs/specs/analyse-[topic].md` if the user wants it persisted.

---

> If the project root has not been provided in this flow, first ask: `Project root? (folder path)`.

## Steps

1. **Identify scope** - a single file, a feature group (adapter + service + helper), a cross-cutting pattern (`Result` flow, boundary mapping, stdout/stderr discipline for a CLI, the config cascade, logging, security, the coupling mode), or the whole project.

2. **Ask when ambiguous** - if the request has several valid readings, use `AskUserQuestion` before diving in. See "When to ask" below.

3. **Read the relevant sources** by layer. First read the use case and the Salesforce coupling from `docs/specs/04-architect.md`, then trace only the layers that exist for it:
   - Contract & specs: `docs/specs/04-architect.md` (structure of truth), other `docs/specs/*`.
   - Shared: `src/config.ts` (`AppConfig` + `resolveConfig`), `src/types.ts` (`Result<T>` + DTOs), `src/errors.ts` (named errors), `src/logger.ts` (pino, where the use case imposes it; log file `~/.<tool>/logs/app.log` for a CLI tool).
   - Composition root / boundary, by use case: `src/cli.ts` (CLI tool: commander bootstrap, global handlers, exit-code mapping) · `src/index.ts` (library: public exports) · `src/server.ts` (service: server bootstrap, global handlers, status-code mapping) · `src/extension.ts` (extension: activation, contributions) · `src/main.tsx` (application: React root, routing).
   - Adapters, by use case: `src/commands/<group>.ts` (CLI) · public modules (library) · route handlers (service) · contribution handlers (extension) · screens and components (application, `@rules/ui.md`). All thin.
   - Services: `src/services/<domain>.service.ts` (business logic).
   - Salesforce (only when coupling is confirmed): `src/sf/runner.ts` (the **only** spawner), `src/sf/helpers.ts` (typed helpers), `src/sf/project.ts` (sfdx-project mode only). `salesforce-cli-reference/index.md` is the command/flag reference, consulted on demand by topic file - never read whole.
   - Output (CLI tool): `src/output/index.ts` (dispatch) + `json.ts` / `table.ts` and, only if shipped, `csv.ts` / `xlsx.ts`.

4. **Trace the flow** following the unidirectional path of the use case. CLI with Salesforce: `cli.ts` (parse) → `commands/<group>` (validate flags) → `services/<domain>` (business rule) → `sf/helpers` → `sf/runner` (`cross-spawn sf [...args, --json]`) → parsed envelope → `Result<T>` → back to the command → `output/` formatter → stdout / file. Other use cases: entry point → adapter (validate input) → `services/<domain>` → (external call or data source) → `Result<T>` → back to the adapter → response / render. **Pinpoint the anchors**: where the `sf` invocation is built (which helper, which catalog topic file verifies its flags; Salesforce only) and where the `Result` / named error maps to the boundary outcome. For a failure path: a service/`sf` layer returns a `Result` failure (`kind: "error"` → CLI exit 1, `kind: "warning"` → CLI exit 0) or raises a named error; the adapter writes `error.message` to the user channel (CLI: stderr); a thrown error reaches the boundary (CLI: `cli.ts` and `toExitCode`, `ValidationError` / commander usage → 2, else 1; service: the error handler, status code per `@rules/errors.md`). For `sfdx-project` mode: the entry point resolves the project once at startup via `src/sf/project.ts`.

5. **Security angle** (always include) - verify and report:
   - Salesforce only: process spawn happens **only** in `src/sf/runner.ts` via `cross-spawn`; no `node:child_process` direct, no `shell: true`, no spawn from a `services`/adapter/`output` module. The `sf` args are an **array** with user values (alias, SOQL, paths) as **discrete elements** - never spliced into a command string.
   - No token/secret is read, stored, or logged; with Salesforce the project holds at most a non-secret alias; a `Result` `message`/`detail` never carries a secret (`@rules/security.md`).
   - A path from input (`--output`, `EXPORT_DIR`, an import/Apex file, an upload) is resolved and confined under the base dir (no traversal); external data is `unknown` then validated; CLI: `stdout` carries data only.

6. **Report** (in the user's language):
   - What the code does (behavior).
   - How it connects across layers (dependencies, data flow, the `sf` call when applicable, the `Result → boundary outcome` mapping).
   - Any inconsistency vs the contract or the rules (`@rules/*`), with the rule named - including security (`@rules/security.md`).
   - `file:line` references.
   - **Flag any unverified assumption explicitly** - do not fabricate a runtime behavior you could not read (an `sf --json` field shape, a live org response, a host API behavior).

## When to ask the user

Use `AskUserQuestion` when:
- **Multiple valid scopes** - "trace the export" could mean the command, the service, the `bulkExport` helper (Salesforce), or the `output/` formatter.
- **Multiple readings** - "how does the query work" - which command or endpoint? the `sf data query` call (Salesforce)? the envelope parse? the `Result` mapping? the formatter?
- **Depth vs breadth** - a deep audit of one feature group vs a survey of several.
- **Output format** - short summary, structured report, or actionable findings list.

Offer 2-4 concrete options, recommended one first. Do not ask when the scope is obvious or you are just confirming a fact.

## Anti-patterns - what NOT to do
- **Do not** modify code during an analysis. This skill is read-only; if a fix is wanted, hand off to `/yarn-fix-issue` or `/yarn-add-feature`.
- **Do not** report a behavior you inferred but did not read - mark it as an assumption and offer to verify.
- **Do not** describe the layers in the abstract - anchor every claim to a `file:line`.
- **Do not** trace a layer the use case does not have (no `src/sf/` without Salesforce coupling, no `output/` outside the CLI tool).
- **Do not** silently pick one interpretation when several exist - ask.
- **Do not** rewrite the README - this skill is read-only; at most flag it stale for a write skill (`@rules/readme.md`).

## When the user asks something adjacent
- **"And fix it"** → switch to `/yarn-fix-issue` (bug) or `/yarn-add-feature` (change), carrying the analysis findings.
- **"Is this secure / well-architected?"** → compare against `@rules/security.md`, `@rules/architecture.md`, `@rules/use-cases.md`, `@rules/sf-cli.md` (Salesforce only), and `docs/specs/04-architect.md`; report deviations, do not refactor (that is `/yarn-refactor-code`, on request).
